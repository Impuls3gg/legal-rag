# legal-rag

Локальный RAG-поиск по законодательству РФ: полностью на своём пайплайне
(без LangChain/LlamaIndex), модели грузятся прямо в процесс через
[transformers](https://huggingface.co/docs/transformers) (никаких внешних
серверов), векторный поиск на FAISS (файл на диске).

## Архитектура

```
источник (data/raw/, Wikisource, pravo.gov.ru) -> RawAct
    -> parser.py: разбор на Раздел/Глава/Статья
    -> chunking.py: Chunk (единица индексации = статья, длинные режутся)
    -> embeddings.py: BAAI/bge-m3 (transformers) -> нормализованный вектор [CLS]
    -> index/faiss_store.py: FAISS IndexFlatIP (cosine) + JSON с метаданными
    -> retrieval.py: поиск top-k чанков по вопросу
    -> llm.py: Qwen2.5-Instruct (transformers), ответ строго по контексту + цитаты [акт, ст. N]
```

## Установка

Нужен [uv](https://docs.astral.sh/uv/). Всё считается на CPU, GPU не требуется.

```bash
uv sync --extra dev
```

`torch` ставится в CPU-сборке из индекса PyTorch (это прописано в
`pyproject.toml`), иначе с PyPI приехали бы CUDA-библиотеки на 2.5 ГБ.

### Модели

| Роль | Модель по умолчанию | На диске | В памяти (CPU) |
|---|---|---|---|
| эмбеддинги | `BAAI/bge-m3` | 2.3 ГБ | ~2.3 ГБ (fp32) |
| генерация | `Qwen/Qwen2.5-1.5B-Instruct` | 3.1 ГБ | ~3.2 ГБ (bf16) |

При первом запуске `transformers` скачает веса с Hugging Face Hub в
`~/.cache/huggingface/`. Если Hub недоступен напрямую — задайте прокси
(`HTTPS_PROXY=...`) или скачайте папку модели любым способом и укажите путь:

```bash
LEGAL_RAG_LLM_MODEL=models/Qwen2.5-1.5B-Instruct uv run python -m legal_rag.cli ask "..."
```

По умолчанию стоит 1.5B, потому что в WSL с лимитом ~7 ГБ ОЗУ обе модели
должны уместиться одновременно. `Qwen/Qwen2.5-3B-Instruct` (~6.2 ГБ в bf16)
заметно лучше рассуждает по юридическим текстам, но требует поднять лимит
памяти WSL (`%USERPROFILE%\.wslconfig`, `[wsl2] memory=11GB`, затем
`wsl --shutdown`):

```bash
LEGAL_RAG_LLM_MODEL=Qwen/Qwen2.5-3B-Instruct uv run python -m legal_rag.cli ask "..."
```

Генерация на CPU идёт со скоростью единиц токенов в секунду: ответ занимает
от полуминуты до пары минут. Для разработки и демо этого достаточно.

`uv sync` создаёт `.venv` и ставит туда сам пакет `legal_rag` и зависимости.
Дальше все команды запускаются через `uv run ...` — отдельно активировать
venv не обязательно.

Тесты (парсер статей и чанкинг — самые хрупкие места пайплайна) прогнаны и
проходят:

```bash
uv run pytest tests/ -q
```

## Наполнение данными (MVP: несколько кодексов)

Три способа, можно сочетать:

1. **Wikisource (самый быстрый старт).** Кодексы на ru.wikisource.org лежат
   постранично по главам в обычном HTML. Скрипт забирает диапазон глав и
   кладёт готовый `text.txt` + `meta.json` в `data/raw/`:
   ```bash
   uv run python scripts/fetch_wikisource.py \
       --page "Гражданский кодекс РФ" --chapters 1-29 \
       --act-id gk-rf-chast-1 \
       --title "Гражданский кодекс Российской Федерации (часть первая)" \
       --number 51-ФЗ --date 1994-11-30
   ```
   Редакция на Викитеке может отставать от актуальной — для отладки пайплайна
   это не важно, для реальной работы сверяйтесь с официальным источником.

2. **Локальные файлы.** Положите текст кодекса в
   `data/raw/<act_id>/text.txt` и опишите акт в `data/raw/<act_id>/meta.json`:
   ```json
   {"title": "Гражданский кодекс РФ (часть первая)", "act_type": "кодекс",
    "number": "51-ФЗ", "date": "1994-11-30", "source_url": "..."}
   ```
   Проще сделать это через `uv run python scripts/add_act.py` — скрипт
   спросит метаданные и попросит вставить скопированный из браузера текст.

   Тексты законов как официальные документы не защищены авторским правом
   (ст. 1259 ГК РФ), так что копировать их для локального использования
   можно свободно. Проверено на практике: и `pravo.gov.ru` (старая система
   с непубличными ID документов), и `docs.cntd.ru` (требует SSO-логин) не
   поддаются автоматическому скрапингу без ручного похода в браузер —
   так что копипаста текста из браузера сейчас реально самый надёжный путь.

3. **pravo.gov.ru.** Поиск на портале построен на JS, поэтому автоматически
   находить акты по названию нельзя — нужно вручную найти акт на сайте,
   скопировать прямую ссылку на текст и добавить в `data/sources.json`
   (формат и вся логика — в `src/legal_rag/ingest/pravo_gov.py`). Селектор
   извлечения текста из HTML там эвристический — почти наверняка потребует
   подстройки под реальную страницу конкретного акта.

## Использование

```bash
uv run python -m legal_rag.cli build-index
uv run python -m legal_rag.cli ask "Каков общий срок исковой давности?"
```

CLI выводит ответ модели и список источников (статьи с оценкой релевантности),
на которые он опирался.

## Структура репозитория

- `src/legal_rag/ingest/` — источники данных и парсер структуры акта
- `src/legal_rag/chunking.py` — разбиение акта на чанки
- `src/legal_rag/embeddings.py`, `llm.py` — обёртки над transformers (bge-m3, Qwen)
- `src/legal_rag/index/` — FAISS-хранилище
- `src/legal_rag/retrieval.py` — поиск top-k по вопросу
- `src/legal_rag/cli.py` — команды build-index / ask
- `scripts/` — загрузка актов (Wikisource, ручная вставка)
- `tests/` — юнит-тесты парсера и чанкинга (самые хрупкие места пайплайна)

## Известные ограничения / что делать дальше

- Парсер статей (`ingest/parser.py`) рассчитан на типовую разметку кодексов
  ("Статья N. Название"). Для актов с нестандартной версткой статьи могут не
  распознаться — `build-index` в этом случае печатает предупреждение.
  Оглавление в начале скопированного текста отбрасывается автоматически
  (признак — нумерация статей, начинающаяся заново), пустые статьи в индекс
  не попадают.
- Длина ответа ограничена `LEGAL_RAG_LLM_MAX_NEW_TOKENS` (512). Контекст
  `TOP_K=6` статей — это 3–5 тыс. токенов, у Qwen2.5 окно 32k, так что
  обрезания нет, но чем больше контекст, тем медленнее генерация на CPU.
- `pravo_gov.py` — best-effort HTTP-скрапер, а не официальный API-клиент;
  требует ручного подбора ссылок и, вероятно, правки CSS-селектора.
- Реранкинг и гибридный поиск (BM25 + вектора) не реализованы — при желании
  улучшить точность это первое, что стоит добавить.
